# Known Issues

- The JobSystem is now dependency-aware (per-worker `System.Threading.Channels` queues + work stealing + a 4096-slot ring; ≤8 dependencies per job; `ScheduleFor` countdown barriers; `Complete` blocks on a semaphore, no busy-wait). Remaining limits: no job priorities, and scheduling more than 4096 outstanding jobs throws `InvalidOperationException`. Burst-scheduling thousands of tiny jobs churns BCL channel segments (measured ~48 B/op at 1024-job bursts); engine-scale batches (≤64/frame) stay at ~0 B — the benchmark uses `Jobs_ScheduleComplete_64` for that reason.
- The batch renderer uploads geometry through a staging buffer every time the geometry changes (per-slot byte-snapshot dirty gate); when it does upload, the staging→device copies are recorded into the main command buffer, so no per-frame queue drain occurs. `vkQueueWaitIdle` remains only for resize, dispose, and rare buffer growth.
- MAILBOX present is non-blocking, so an unpaced CPU renders as fast as it can and presents every completed frame (the 60 Hz fixed-step sim renders multiple times per present) — `--cap <fps>` restores a steady cadence. Sim-to-present interpolation is a deferred optional follow-up for refresh-rate-independent smoothness (see `docs/FramePacingPlan.md`).
- `SpritePacket.Texture` is honored by the batch renderer via per-texture-range descriptor binds (a draw per distinct texture range — no sorting/merging yet, so interleaved textures multiply draw calls). `SpritePacket.Material` is still ignored; only one descriptor layout (combined image sampler in set 0) exists. Texture uploads are startup-only; atlases, bindless, and per-frame uploads are out of scope.
- Asset loading (PNG via StbImageSharp) is synchronous and decodes into a managed `byte[]`, and entity/tile textures live in the sample (`TextureLibrary`) rather than a shared engine asset layer — the `docs/Conventions/Assets.md` design targets (unmanaged decode, async I/O, atlases/bindless) remain future work.
- Tile borders are drawn by overdrawing a slightly larger black diamond behind each white tile (~2px).
- Capped runs (`--cap 60`/`--cap 30`) show a single **non-main** thread burning ~60-95% of a core at `TimeCritical` priority with `ThreadState=Running` even though the main loop measures correct sleeps/wait (cap30 → `avgWait≈30 ms`). The busy thread is not the window thread, not created by any repo code (no `ThreadPriority`/`timeBeginPeriod` usage anywhere), and pre-dates the frame-pacing rework — it is attributed to the GPU-driver present/queue thread busy-waiting under MAILBOX present on this machine/driver. Uncapped runs are ~5-6% of a core. Revisit if a future swapchain/present-mode change or a different driver reproduces lower CPU.
