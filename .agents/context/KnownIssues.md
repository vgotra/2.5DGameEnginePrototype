# Known Issues

These are current limitations, not failed milestones. Follow-up candidates that require new runtime work are listed in `Roadmap.md`.

## Validated Runtime Limitations

- The JobSystem uses per-worker `System.Threading.Channels` queues, work stealing, pooled parallel-for chunks, and a 4096-slot outstanding-job limit. `Run`/`ParallelFor` work is waited synchronously through a semaphore without busy-waiting. Scheduling more than 4096 outstanding jobs throws `InvalidOperationException`. Burst-scheduling thousands of tiny jobs churns BCL channel segments; engine-scale batches remain the supported workload.
- The batch renderer uploads geometry through a staging buffer every time the geometry changes (per-slot byte-snapshot dirty gate); when it does upload, the staging→device copies are recorded into the main command buffer, so no per-frame queue drain occurs. `vkQueueWaitIdle` remains only for resize, dispose, and rare buffer growth.
- MAILBOX present is non-blocking, so an unpaced CPU renders as fast as it can and presents every completed frame (the 60 Hz fixed-step sim renders multiple times per present) — `--cap <fps>` restores a steady cadence. Sim-to-present interpolation is a deferred optional follow-up for refresh-rate-independent smoothness (see the `game-loop-frame` skill).
- `SpritePacket.Texture` is honored by the batch renderer via per-texture-range descriptor binds (a draw per distinct texture range — no sorting/merging yet, so interleaved textures multiply draw calls). Non-zero `SpritePacket.Material` values select descriptor-backed texture resources, and additive sprites use a dedicated pipeline. Independent material shader parameters, material asset loading, and state sorting remain future work. Texture uploads are startup-only; bindless and per-frame uploads are out of scope.
- Renderer command-preparation audit coverage is CPU-side and validates deterministic work/chunk parity; GPU driver timing and live Vulkan command-buffer timing remain environment-dependent. Live batch recording currently uses one serial secondary command buffer; parallel recorder infrastructure remains available for future measured workloads.
- Asset loading (PNG via StbImageSharp) is synchronous and decodes into a managed `byte[]`, and entity/tile textures live in the sample (`TextureLibrary`) rather than a shared engine asset layer — the `assets-io` skill's design targets (unmanaged decode, async I/O, atlases/bindless) remain future work.
- Tile borders are drawn by overdrawing a slightly larger black diamond behind each white tile (~2px).
- Capped runs (`--cap 60`/`--cap 30`) show a single **non-main** thread burning ~60-95% of a core at `TimeCritical` priority with `ThreadState=Running` even though the main loop measures correct sleeps/wait (cap30 → `avgWait≈30 ms`). The busy thread is not the window thread, not created by any repo code (no `ThreadPriority`/`timeBeginPeriod` usage anywhere), and pre-dates the frame-pacing rework — it is attributed to the GPU-driver present/queue thread busy-waiting under MAILBOX present on this machine/driver. Uncapped runs are ~5-6% of a core. Revisit if a future swapchain/present-mode change or a different driver reproduces lower CPU.
- Sparse ECS limits: queries support at most three component types (`Query<T1,T2,T3>`) and do not yet support excluded or exact-type filters. Parallel queries are opt-in; fixed-step movement, collision, and order-sensitive gameplay remain serial. `World.Get<T>` on a stale or destroyed entity throws rather than returning safely; callers must validate entity ownership when using the fast API. Component add/remove changes dense stores and may allocate during capacity growth; steady-state gameplay avoids structural changes in hot loops.
